# R6.3 关系生成分项 profiling（2026-11-18）

工具 `scripts/profile_resource_access.py`，纯逻辑合成行，**不开启
tracemalloc**（插桩影响见第 3 节），15 次重复，逐阶段 p50。原始数据见
`resource-access-profile-r63-2026-11-18.json`。工具不是门禁。

## 1. 分项结果（ms，p50）

| 阶段 | 8 行 | 64 行 | 512 行 |
| --- | --- | --- | --- |
| access index 构建 | 0.051 | 0.411 | 3.971 |
| resource grouping | 0.001 | 0.006 | 0.045 |
| writer index（排序 + 事件表） | 0.002 | 0.009 | 0.053 |
| candidate search（bisect 计数） | 0.002 | 0.012 | 0.081 |
| edge generation（轻量迭代） | 0.015 | 0.399 | 39.018 |
| relation construction / 物化 | 0.049 | 0.819 | 68.161 |
| explanation（采样 64 条） | 0.047 | 0.322 | 0.444 |
| **JSON serialization（整图）** | 0.198 | 6.326 | **519.259** |
| query filtering（整图筛选） | 0.006 | 0.188 | 22.189 |

512 行产生 33,024 条候选与 33,024 条边，无重复、无跨资源边。

## 2. 瓶颈归因

- 候选匹配（0.081ms）与 writer 索引（0.053ms）几乎不计；R5.1 的 bisect
  与分组已经把这部分成本降到可忽略。
- 边生成 39ms、关系物化 68ms，二者与边数线性相关，但不是最大项。
- **整图 JSON 序列化 519ms 才是 512 规模的主成本**；查询过滤 22ms。
- explanation 为按需生成，采样 64 条仅 0.44ms，证明 R5.2 的惰性策略有效。

## 3. 对先前 benchmark 口径的修正（重要）

R4.3 / R5.1 的 benchmark 在 `tracemalloc` 开启期间计时。对照实测（512
行、8 次重复、仅图构建）：

| 条件 | p50 |
| --- | --- |
| tracemalloc 关闭 | **63.7ms** |
| tracemalloc 开启 | **626.3ms** |

约 10 倍的差异来自逐分配插桩，**不是算法本身的成本**。因此：
R5.1 记录的「analysis p50 667ms」不能解释为纯算法耗时；它是插桩下的
观测值。峰值内存数据（29.6MB / 5.5MB）仍然有效，因为 tracemalloc 正是
测量它的手段。后续性能结论必须同时给出是否开启插桩。

## 4. 对下一步的建议（R6.4）

优化目标应从「重写 writer×reader 枚举」改为**避免不必要的整图序列化与
物化**：把查询条件下推到生成阶段、按需构造解释、对汇总请求不构造完整
relation 对象。该建议由上述分项数据支持，而非预先假设。

真实 capture 基线（R6.1）显示 N3-05A1/A2 均产生 0 条 writer→reader 边，
因此本优化只针对合成大图/未来大负载能力，不被宣称解决真实 capture 的
已观测瓶颈。
