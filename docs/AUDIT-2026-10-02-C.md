## 2. 本轮新引入的缺陷（4 项，全部由实现方造成）

### F1 — 报告 schema 漂移被加重（最严重）

本轮为 pipeline report 的 gate 行新增了 `lint` 子记录。而
`docs/CI-ORCHESTRATION-CONTRACT.md` §6.1 的必备会计字段表**连已有的
`process_exit_code` / `execution_clean` / `blocking` / `command` / `detail` /
`tests_executed` 都没有列出**。

即 §6.1 的 schema drift 并非「待处理的历史问题」——本轮**往一个未对齐的 schema
上又加了一个字段**。

### F2 — 只升了一个 schema 版本，漏了另一个

`release-gates` 由 `/5` 升为 `/6`（因为 gate 行可携带子记录），但
`ci-pipeline` 仍是 `/3`、`ci-pipeline-report` 仍是 `/2`，尽管本轮同样向
pipeline report 增加了字段。同一次改动中两套 schema 的版本纪律不一致。

### F3 — 实现方自身的分类与自身状态矛盾，且无控制能抓

**status: OPEN / CLASSIFICATION-CONSISTENCY GAP**

```
docs/LINT-EXECUTION-CONTRACT.md
  freshness_policy: living   ← 语义：必须与当前状态一致
  status: FROZEN             ← 语义：内容不再变更
```

该文档在 `proposed` 时标为 `living`（当时正确），改为 `implemented` / `FROZEN`
后未重审分类。**分类控制只校验 schema 字段本身，从不与正文的 `status:` 交叉
核对** —— 这与本轮反复出现的「控制被被检查对象满足 / 近似命中」属同一类。

**不得自行裁决**。`freshness_policy` 与 `status` 并不表达完全相同的维度，
仅凭字符串冲突不足以断言非法；而在既有 classification/freshness 体系内，
二者如何共存尚未定义。**既不采用「FROZEN 覆盖 living」，也不采用
「living 覆盖 FROZEN」** —— 二者都是先选答案再找理由。

缺的不是一条矛盾检测控制，而是**共存规则本身**：一个自称内容不再变更的
文档应当声明哪种 freshness_policy，取决于「冻结」指的是规范文本冻结，
还是治理状态冻结。规则定下来之前，交叉控制无从写起。

### F4 — drift 界已失准

**status: OPEN / CALIBRATION GAP**

审计时 `declared=1 / actual=2`，距 FAIL 剩 3 次提交。该界在本会话**触发了两次**。
一个每 2 次提交即报警的界是例行噪音，不再是陈旧度信号。它是为修「不可达的等值
规则」而引入的，此后持续提交却未重新校准。

**这是控制校准问题，不是当前生产事实缺陷。** 今日 PASS 只证明当前状态没有
触发问题，不证明该阈值在长期运行中仍有区分度。

**不得为了让报告干净而直接调阈值。** 窗口该多宽取决于一个尚未回答的问题：
状态文档应在「每次提交后」还是「每个里程碑后」刷新。当前刷新节奏本身没有
被声明过 —— drift 界一直在测量一个节奏未定的流程。校准的前提是先声明节奏。
